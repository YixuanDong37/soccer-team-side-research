# 运行手册

按顺序做。命令都在 Git Bash 里运行（Windows）。时间是原机器上的实测或记录值（一块 RTX 50 系显卡，5 个并行进程），只作参考。

约定：

```bash
PKG=<本文件夹的绝对路径>          # 例如 D:/code/gbf/reid-lab
PY=<gbf 仓库>/.venv/Scripts/python.exe
```

实验台的脚本一律加 `-I` 运行（隔离模式，不读环境变量里的 Python 路径）。`fuse_r1` 里的脚本再加 `-B`（不在别的部件文件夹里留下 `.pyc`）。

## 0. 需要准备什么

| 要做的事 | 需要 |
|---|---|
| 只读文档和结果 | 什么都不用装 |
| 第 3 到 7 节（实验台） | gbf 的 Python 环境（Python 3.12，numpy、pandas、scipy、pyarrow，并装好 gbf 本身）；13 段的运行结果；SN-GSR 标注（打分和拟合时用） |
| 第 2 节（生成运行结果） | 另外还要：sn-gamestate 的环境（torch 2.7.1+cu128、tracklab 1.3.24、prtreid、bpbreid、easyocr、ultralytics）、ffmpeg 和 ffprobe、显卡、SN-GSR-2025 训练集压缩包 |

实验台只导入 gbf 的基础模块（`gbf.evaluate` 等），不导入 `gbf.relink`。gbf 仓库用 fork 的 `relink` 分支即可。

## 1. 改路径（必须先做）

代码里写死了原机器的绝对路径，一共涉及约 400 个文件。`relocate.py` 把它们改成你机器上的位置。

```bash
cd $PKG
python relocate.py --show          # 看有哪些位置、原来的值是什么（不改任何东西）
python relocate.py --dry-run --runs D:/data/gsr-runs --runs-leadcfg D:/data/gsr-runs-leadcfg \
    --gsr-train D:/data/sn-gsr-2025/train --gbf-repo D:/code/gbf --sngs D:/code/sn-gamestate
                                   # 先预演：只报告会改多少处
python relocate.py --runs D:/data/gsr-runs --runs-leadcfg D:/data/gsr-runs-leadcfg \
    --gsr-train D:/data/sn-gsr-2025/train --gbf-repo D:/code/gbf --sngs D:/code/sn-gamestate
python relocate.py --check         # 应输出 no absolute path outside the configured locations，退出码 0
```

用时几秒钟。每个参数的意思：

| 参数 | 含义 | 不给时 |
|---|---|---|
| `--runs` | 原来的跟踪设置下，各段运行结果所在的文件夹（里面是 `SNGS-107/` 等） | 保持原机器的值 |
| `--runs-leadcfg` | 负责人的跟踪设置下的运行结果文件夹 | 保持原值 |
| `--gsr-train` | 解压后的 SN-GSR 训练片段（每段有 `img1/` 和 `Labels-GameState.json`） | 保持原值 |
| `--gbf-repo` | gbf 仓库的位置 | 保持原值 |
| `--sngs` | sn-gamestate 的位置 | 保持原值 |
| `--python` | 运行实验台的 Python | `<gbf-repo>/.venv/Scripts/python.exe` |
| `--tools-root` | 包含 `reid_lab/` 的文件夹 | `<本文件夹>/method` |
| `--pipeline-root`、`--evidence-root`、`--patch-dir` | 输入流程、历史材料、补丁的位置 | 本文件夹里对应的子文件夹 |
| `--leadcfg-root` | 负责人设置专用的实验台副本（第 6 节会生成） | `<本文件夹>/_leadcfg` |
| `--gsr-root` | SN-GSR 数据集的文件夹 | `--gsr-train` 的上一级 |
| `--config 文件.json` | 把上面的值写在一个 JSON 里，见 [relocate.example.json](../relocate.example.json) | |

要知道的几点：

- **直接改文件。** 改完后本文件夹里约 400 个文件会和仓库里的版本不同，这是预期的；不要把改过路径的文件提交回仓库。想保持仓库干净，就加 `--dest 另一个文件夹`：脚本会先把整个文件夹复制过去，只改副本。
- **可以重复运行。** 每次运行都会写 `relocate-log.json`，记下现在文件里用的是什么值、改了哪些文件、每个文件改之前和之后的 sha256。换位置时带上新的值再跑一遍即可。
- **没给的位置不会改。** `--check` 会把它们列出来，并提示该加哪个参数。
- **不会改的文件：** `pipeline/patches/*.patch`（来源记录里登记了它们的 sha256，必须原样）、`relocate.py` 自己、`manifest-sha256.txt`。
- **路径里不要有空格。** 有几行脚本没有给路径加引号。
- **不带盘符的写法。** `run_gsr_clip*.sh` 里有一行不带盘符的路径（例如 `/data/gsr-runs/...`），因为 tracklab 用冒号切分视频地址，不能出现盘符。所以跑输入流程时，Git Bash 的当前盘必须和运行结果文件夹在同一个盘。
- **校验文件。** `python relocate.py --verify-manifest` 对照 `manifest-sha256.txt`，会分别报告“和交付时一样”“被 relocate.py 改过”“不一样”的文件数。

## 2. 生成输入：13 段的运行结果

如果你已经有这 13 段的运行结果，跳到第 3 节。这一节需要联网下载模型和数据，需要显卡。

### 2.1 第三方环境

1. 取 sn-gamestate（提交 `1c958345067218297d221e45e1a6405f975f83e0`），在它的目录里应用补丁：
   ```bash
   cd <sn-gamestate> && git apply $PKG/pipeline/patches/sn-gamestate-local-v2.patch
   ```
   然后把 `pyproject.toml` 里 `prtreid @ file:///...` 和 `torchreid @ file:///...` 两行改成你本地 prtreid、bpbreid 的位置（补丁里是原机器的位置，补丁文件本身不能改）。
2. 取 prtreid（提交 `30617a75967e84d5d516959c4b84cbeea6f56493`）和 bpbreid（提交 `a2dc4304284784d8b2c061764512f0698aa38c21`），分别应用 `prtreid-local.patch` 和 `bpbreid-local.patch`（各一处：不编译只在评估时用的 Cython 扩展）。
3. 在 sn-gamestate 里建 `.venv` 并安装。版本和每个改动的说明见 [provenance-gsr.json](../pipeline/gsr/provenance-gsr.json)。
4. 下载模型权重：`bash $PKG/pipeline/fetch_weights.sh`。脚本最后打印校验值，对照 `provenance-gsr.json` 里的 `weights_sha256`。
5. `sn-gamestate-local.patch` 是补丁的第一版，只留作记录；用 `-v2` 那个。

### 2.2 数据

1. 自己从 Hugging Face 下载 SN-GSR-2025（版本 `ce84ee7d9acb2f9fe999ceed2b38e303ffa5efb9`）的 `train.zip`，sha256 应为 `f216ebed0347f5af52ee7d975a9b5f6f33b5370bdbed75dd1aded9f8b5ae8316`，约 9.76 GB。
2. 只解压选中的片段：
   ```bash
   $PY -I $PKG/pipeline/gsr/prepare_gsr.py <train.zip> f216ebed0347f5af52ee7d975a9b5f6f33b5370bdbed75dd1aded9f8b5ae8316 \
       <gsr-train 文件夹> <新的 selection.json>
   ```
   它按固定顺序选出 50 段并解压，同时写出一份选择表。新写出的选择表里 `order` 和 `selected` 应该和带来的 [pipeline/selection.json](../pipeline/selection.json) 一样。实验台用的 13 段是 `selected` 的前 13 个：`SNGS-107 163 106 097 067 100 066 161 169 162 151 102 112`。

### 2.3 跑原来的跟踪设置

```bash
bash $PKG/pipeline/gsr/run_gsr_batch.sh $PKG/pipeline/selection.json \
    SNGS-107 SNGS-163 SNGS-106 SNGS-097 SNGS-067 SNGS-100 SNGS-066 SNGS-161 SNGS-169 SNGS-162 SNGS-151 SNGS-102 SNGS-112
```

- 每段 8 步：生成 720p 视频、跟踪（插件）、球检测、导出、gbf（导入、分镜头、refine）、导出外观向量、外观配对、对照标注的检查。
- 每段 350 到 810 秒，13 段约 2 小时。每段最多 75 分钟，超时或失败会记进 `<runs>/batch.log`，然后继续下一段。
- 可以续跑：每完成一步留下 `<runs>/<片段>/.done-<步骤>`；重做某一步会清掉它后面各步的标记。
- 单独跑一段：`bash $PKG/pipeline/gsr/run_gsr_clip.sh SNGS-107`。
- 13 段的汇总：`$PY -I $PKG/pipeline/analysis/gsr_summary.py <runs> $PKG/pipeline/selection.json <输出.json>`。

实验台从每段读这些文件：`gbf/refine/tracks.parquet`、`gbf/refine/calib.parquet`、`gbf/refine/refine.json`、`gbf/cuts.json`、`reid-embeddings.npz`、`appearance-match.json`、`reentry-eval.json`。

### 2.4 跑负责人的跟踪设置

需要先有 2.3 的结果（720p 视频和球检测结果直接从那边复制，保证输入画面完全相同）。

```bash
bash $PKG/pipeline/gsr/run_gsr_batch_leadcfg.sh \
    SNGS-107 SNGS-163 SNGS-106 SNGS-097 SNGS-067 SNGS-100 SNGS-066 SNGS-161 SNGS-169 SNGS-162 SNGS-151 SNGS-102 SNGS-112
```

结果写到 `--runs-leadcfg` 指定的文件夹。每段结束时脚本会检查四处改动确实生效（见 [run_tracklab_leadcfg.py](../pipeline/run_tracklab_leadcfg.py) 开头的说明），没生效就报错。这套设置是读懂负责人运行包之后重新实现的，和负责人的运行环境仍有差别，见 [局限.md](局限.md) 第 5 节。

## 4. 用带来的参数重新生成结果（约 4 到 8 分钟）

不重新拟合，只验证“同样的参数 + 同样的输入 = 同样的结果”。

```bash
cd $PKG/method/reid_lab/work/fuse_r1
$PY -I -B prep.py 5          # 算证据表，写进 cache/。没有缓存时实测 2 分 33 秒
$PY -I -B method.py          # 写出 10 个 METHOD_*.json。实测 36 秒
for p in strict balanced recall fixed_strict fixed_balanced fixed_recall frozen_strict frozen_balanced frozen_recall cuts_only; do
  $PY -I $PKG/method/reid_lab/score.py METHOD_$p.json OUT_$p.json || echo "FAILED $p"
done                          # 每个约 20 秒
```

期望：10 个 `METHOD_*.json` 和 10 个 `OUT_*.json` 的内容和带来的完全一样。比较时忽略行尾差别（Windows 上的 Python 会写出 CRLF，仓库里是 LF）：

```bash
git -C $PKG diff --stat --ignore-cr-at-eol -- method/reid_lab/work/fuse_r1      # 应该只剩改过路径的文件
```

没有 git 时用 `diff --strip-trailing-cr 旧文件 新文件`。打分结果应为：稳妥档 67 / 3 / 67，均衡档 85 / 5 / 47，多认档 106 / 7 / 24（完整的表见第 9 节）。

`prep.py` 的参数 5 是并行进程数。`cache/` 里是中间结果（pkl），可以随时删掉重算。

## 5. 从头重新拟合（约 12 到 20 分钟）

建议在副本里做（`python relocate.py --dest <副本> ...`），这样带来的参数还在，方便比较。

```bash
W=<副本>/method/reid_lab/work
# 5.1 删掉带来的拟合结果和缓存
rm -f  $W/m_cuts/final_params.json $W/m_cuts/loco_params.json
rm -rf $W/m_cuts/methods; mkdir -p $W/m_cuts/methods
rm -rf $W/m_space/params_cache $W/m_space/params_all13.json $W/m_space/params_loco.json
rm -rf $W/fuse_r1/cache $W/fuse_r1/params_loco.json $W/fuse_r1/METHOD_*.json $W/fuse_r1/OUT_*.json

# 5.2 三个部件，按这个顺序
(cd $W/m_cuts  && $PY -I make_methods.py)          # 约 45 秒：切开模型，每折一套 + 全部 13 段一套
(cd $W/m_space && $PY -I run_position_linker.py)   # 约 70 秒：位置模型
(cd $W/m_space && $PY -I posscore.py)              # 约 35 秒：合成要用的 params_cache/excl_*.json
# 外观部件在最终流程里不用拟合

# 5.3 合成
cd $W/fuse_r1
$PY -I -B prep.py 5          # 约 2.5 分钟
$PY -I -B fit_loco.py 5      # 5 到 14 分钟：13 折的配对模型和规则 B -> params_loco.json、out/loco_report.json、out/tradeoff.md
$PY -I -B method.py          # 约 0.5 到 2.5 分钟
# 然后像第 4 节那样打分
```

期望和带来的文件内容完全一样（忽略行尾）的有：`m_cuts/{loco_params,final_params}.json`、`m_cuts/methods/*.json`、`m_cuts/results.*`、`m_space/{params_loco,params_all13}.json`、`m_space/params_cache/excl_*.json`、`fuse_r1/params_loco.json`、`fuse_r1/out/loco_report.json`、`fuse_r1/out/tradeoff.md`、10 个 `METHOD_*.json` 和 10 个 `OUT_*.json`。原机器上从空缓存完整重跑过两次，结果逐字节相同（[evidence/v_repro_1/README.md](../evidence/v_repro_1/README.md)）。

不在这条链里的文件：`m_cuts/cutlink_params.json`、`m_cuts/results_cutlinks.*` 和 `m_cuts/methods/` 里名字带 `cutlinks` 的文件由 `eval_cutlinks.py` 写出；`m_cuts/loco_models.json` 由 `loco.py` 写出（约 15 分钟）。最终方法不读它们，5.1 删掉 `methods/` 之后要再跑 `eval_cutlinks.py` 才会重新出现。

各脚本的完整说明和更多命令在 [fuse_r1/README.md](../method/reid_lab/work/fuse_r1/README.md) 的 “Commands” 一节。其中 `check_r0.py` 需要第一轮（`evidence/fuse`）的缓存，缓存没带，要先在 `evidence/fuse` 里重跑它的 `prep.py` 和 `fit_loco.py` 才能用。

## 6. 负责人设置下的两种结果（T 约 6 分钟，R 约 12 分钟）

负责人设置的运行结果在另一个文件夹里，所以要用实验台的一个副本去读它。副本不随包带，用工具生成：

```bash
cd $PKG
python relocate.py make-lab                         # 生成 _leadcfg/reid_lab：代码和参数复制一份，只是改读负责人设置的运行结果
bash pipeline/leadcfg/run_leadcfg_eval.sh T         # T：原参数照搬
bash pipeline/leadcfg/run_leadcfg_eval.sh R         # R：同样流程重新拟合（会删掉副本里的参数和缓存，只动 _leadcfg 里的东西）
```

- T（transfer）：用原来拟合好的参数，一个数都不改，直接用在新的运行结果上。
- R（refit）：把第 5 节的流程在新的运行结果上重做一遍。R 需要 T 先跑完。
- 输出在 `_leadcfg/reid_lab/out_T`、`out_R`、`eval-logs`。
- 期望：`out_T`、`out_R` 里的 `METHOD_*.json` 和 `OUT_*.json` 与带来的 [results/leadcfg-settings/out_T](../results/leadcfg-settings/out_T/)、[out_R](../results/leadcfg-settings/out_R/) 内容相同（忽略行尾）。
- 13 段负责人设置的运行结果必须都跑完（每段有 `.done-eval`），否则脚本直接退出。
- `make-lab` 可以加 `--dest 别的文件夹` 和 `--runs-dir 别的运行结果文件夹`。目标文件夹非空时会拒绝，除非加 `--force`（只覆盖，不删除）。

## 10. 常见问题

- **`ModuleNotFoundError: reid_lab` 或找不到文件。** 没跑 `relocate.py`，或者移动了文件夹之后没有重跑。运行 `python relocate.py --check`。
- **`ModuleNotFoundError: gbf`。** `$PY` 不是装了 gbf 的那个环境。
- **`... is not a dev clip`。** `data.py` 只认 13 段开发片段。要处理别的片段，用产品版 `gbf.relink`。
- **结果文件“不一样”。** 先确认是不是只有行尾不同（见第 4 节的比较方法）。
